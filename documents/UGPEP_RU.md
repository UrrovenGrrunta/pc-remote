# UGPEP – UrrovenGrrunta Python Enhancement Proposal

**Название:** Руководство по стилю для Python-кода сомнительной психической стабильности  
**Автор:** UrrovenGrrunta  
**Статус:** К сожалению, активен  
**Тип:** Процесс  
**Требуется:** PEP 8, здравый смысл и иногда доступ к паранормальному

## Введение

UGPEP — альтернативное проектное руководство по стилю для Python-кода.

Он следует общим принципам PEP 8 и не пытается его заменить. UGPEP определяет дополнительные соглашения по форматированию, процессу разработки, документированию неудачных подходов и ситуациям, которые недостаточно подробно покрываются обычными инженерными стандартами.

Если UGPEP явно не устанавливает иное правило, следует придерживаться PEP 8.

Главная цель — читаемость. Последовательность и правила важны, но ни одно из них не важнее понимания кода. Разработка программного обеспечения не обязана быть занятием без чувства юмора.

## Глупая последовательность всё ещё остаётся глупой

Руководство по стилю существует, чтобы код было проще читать, а не чтобы предоставить дополнительные способы провалить code review.

Правила UGPEP не следует применять, если это явно делает код менее читаемым. Последовательность внутри проекта предпочтительна, но исключения допустимы, когда они оправданы читаемостью, поддерживаемостью, совместимостью или здравым смыслом.

Если нарушение правила форматирования делает код очевидно понятнее — нарушьте правило. Если объяснить причину невозможно — следуйте правилу.

## Структура кода

### Отступы

Используйте четыре пробела на каждый уровень отступа. Табуляцию для отступов использовать не следует.

Строки продолжения должны визуально отличаться от окружающего кода и делать структуру выражения очевидной.

### Максимальная длина строки

UGPEP следует рекомендациям PEP 8 по длине строк.

Однако цель ограничения длины строки — читаемость, а не соответствие счётчику символов. Длинные выражения следует разбивать на несколько строк, когда это делает их структуру понятнее.

```python
some_path = (
    base_directory
    / "some_directory"
    / "another_directory"
    / "some_file.txt"
)
```

Не рекомендуется разбивать выражение только потому, что оно превышает рекомендованный лимит, если результат становится менее читаемым. Аналогично, нет необходимости оставлять выражение в одну строку лишь потому, что оно технически помещается в лимит.

> Длина строки — ограничение ради читаемости, а не спортивная дисциплина.

### Бинарные операторы

Если длинное выражение разбито на несколько строк, бинарные операторы обычно следует располагать перед выражением, к которому они относятся:

```python
total = (
    first_value
    + second_value
    + third_value
)
```

Как и в остальных разделах UGPEP, читаемость важнее механического соблюдения правила.

### Пустые строки

Пустые строки должны разделять логически разные части файла. Они должны помогать видеть структуру, а не просто удовлетворять формальному количеству пустых строк.

Связанные операции могут оставаться визуально близко друг к другу. Несвязанные операции следует отделять достаточно явно, чтобы переход между ними был понятен.

> Пустая строка — это пунктуация для кода. Используйте её соответственно.

## Импорты

Импорты обычно должны находиться в начале файла, после комментариев уровня модуля и docstring, если они присутствуют.

В UGPEP импорты должны визуально формировать **Лесенку импортов**.

Сначала идут обычные `import`-выражения, обычно расположенные от визуально более коротких строк к более длинным:

```python
import os
import time
import subprocess
```

Затем идёт одна пустая строка, после которой располагаются `from ... import ...`, также от визуально более коротких к более длинным:

```python
from pathlib import Path
from http.server import HTTPServer
from subprocess import CalledProcessError
```

Полный блок импортов желательно оформлять так:

```python
import os
import time
import subprocess

from pathlib import Path
from http.server import HTTPServer
from subprocess import CalledProcessError
```

Лесенка является визуальной, а не алфавитной. Её цель — сделать блок импортов сразу узнаваемым и удобным для просмотра.

Логическая группировка может иметь приоритет, если строгое расположение по длине ухудшает понимание связанных импортов. Лесенка должна организовывать импорты, а не превращаться в архитектурное требование.

Wildcard-импорты следует в целом избегать, если API явно не требует их или не получает от них значимой пользы.

## Именование

UGPEP в целом следует обычным Python-соглашениям:

- функции и переменные используют `snake_case`;
- классы используют `PascalCase`;
- константы используют `UPPER_CASE`.

Имена должны передавать назначение. Более длинное имя не становится автоматически лучше, а оригинальное название, придуманное поздно ночью, не становится документацией само по себе.

## Комментарии

Комментарии должны объяснять, почему что-либо существует, когда это нельзя легко понять из самого кода.

Не следует комментировать очевидные действия:

```python
offset += 1  # Увеличить offset на один.
```

Предпочтительно добавлять отсутствующий контекст:

```python
# Пропустить байт типа сжатия перед чтением checksum.
offset += 1
```

Комментарии могут содержать юмор, если полезная информация остаётся ясной. Шутка рядом с документацией допустима; шутка вместо документации — нет.

## Экспериментальный код

Временно некрасивый код допустим во время исследования, отладки, reverse engineering или работы с недокументированными, повреждёнными, проклятыми, паранормальными или иным образом враждебными системами.

Рекомендуемый процесс:

```text
заставить работать
    ↓
доказать, что работает
    ↓
понять, почему работает
    ↓
отрефакторить
```

Преждевременный рефакторинг не рекомендуется, пока исследуемое поведение не понято. Красиво структурированный неправильный код всё равно остаётся неправильным.

После понимания поведения экспериментальный код теряет дипломатический иммунитет и должен быть отрефакторен. Отладочный вывод следует удалить или заменить нормальным логированием, а устаревшие эксперименты — убрать.

Исторически значимые неудачи вместо этого могут быть сохранены согласно разделам о кладбище и журнале событий.

## Кладбище

Программное обеспечение умирает. Библиотеки перестают подходить, подходы проваливаются, эксперименты забрасываются, а иногда целая реализация живёт всего несколько минут, прежде чем реальность её убивает.

UGPEP разрешает документировать такие потери в кладбище проекта. Рекомендуемое расположение:

```text
UGPEP-logs/graveyard.txt
```

Запись должна указывать погибшего, время его рождения или принятия в проект, время смерти, причину смерти, важные осложнения и последние слова, если они известны.

```text
#               R.I.P
#          <имя погибшего>
# <дата/время рождения> - <дата/время смерти>
# Причина смерти: <техническое объяснение>
# Осложнения: <необязательно>
# Последние слова: <необязательно>
```

### Требования для захоронения

Не следует объявлять что-либо погибшим только потому, что оно временно не используется. Импорт, ожидающий своей смены, не умер. Раздражающая зависимость не умерла.

Подход, который убедительно доказал свою непригодность или был окончательно заменён другой реализацией, может быть объявлен погибшим.

Кладбище сохраняет историю разработки; это не список всего, что разработчику сейчас не нравится.

### Протокол двуязычного захоронения

Смерть — международное явление.

Исторически значимую человекочитаемую информацию в кладбище следует сохранять на языке оригинальной записи и сопровождать переводом.

Если автор пишет запись по-русски:

```text
# Причина смерти: Понижение версии ничего не изменило.
# (Cause of death: Downgrading changed absolutely nothing.)
```

Если оригинал написан по-английски:

```text
# Cause of death: The parser failed immediately.
# (Причина смерти: Парсер сразу завершился с ошибкой.)
```

Это правило особенно относится к причинам смерти, осложнениям, последним словам и исторически значимым описаниям.

Оригинальный текст идёт первым. Перевод следует в скобках. Перевод существует для доступности, а не для переписывания или смягчения оригинала. Смысл, терминология и приблизительный тон должны сохраняться.

### Надгробия в исходном коде

Сразу после смерти компонента в исходном коде допускается временное надгробие:

```python
#               R.I.P
#              library
# 18/08/2026 (01:00) - 18/08/2026 (02:00)
```

После нормального документирования смерти в `graveyard.txt` надгробие обычно следует удалить из production-кода.

> Кладбище хранит погибших. Исходное дерево проекта не обязано становиться кладбищем.

## Журнал событий

Исторически значимые происшествия разработки могут документироваться отдельно от смертей. Рекомендуемое расположение:

```text
UGPEP-logs/events.txt
```

UGPEP определяет два типа событий: `EVENT` и `UPDATE`.

### EVENT

`EVENT` фиксирует произошедшее событие. Обычная запись содержит дату и время, название, перевод при необходимости, описание, доказательства, вывод и статус.

### UPDATE

`UPDATE` фиксирует новую информацию о более раннем событии. Обычная запись содержит дату и время, название, перевод при необходимости, описание, предыдущий статус, текущий статус и итоговый статус.

Исторические записи нельзя молча переписывать только потому, что позднее появились доказательства ошибочности раннего вывода. Оригинальное событие описывает то, что было известно тогда; обновление описывает то, что стало известно позже.

Ошибочные выводы являются частью истории отладки, если они честно отражают имевшиеся в тот момент доказательства.

## Доказательства при отладке

Юмор никогда не должен заменять технические доказательства.

Юмористическое объяснение может сопровождать результат отладки, но сам результат должен оставаться воспроизводимым. Вывод, основанный только на подозрительных ощущениях, недостаточен, если эти ощущения нельзя стабильно воспроизвести, измерить, независимо проверить и желательно покрыть unit-тестами.

## Paranormal-Driven Development

**Paranormal-Driven Development (PDD)** — экспериментальная методология разработки, применимая, когда обычной отладки, коммуникации или рассуждений становится недостаточно и информация получается паранормальными средствами.

PDD не привязан к конкретному способу связи. Возможные интерфейсы включают, но не ограничиваются:

- досками Уиджи;
- spirit box;
- старыми или модифицированными радиоприёмниками;
- EVP-записями;
- необъяснимыми электронными помехами;
- автоматическим письмом;
- повторяемыми стуками или физическими сигналами;
- другими достаточно паранормальными способами коммуникации.

Средство связи следует считать транспортным уровнем. Паранормальную сущность следует считать недокументированной внешней зависимостью. Ни одному из них не следует доверять по умолчанию.

### Проверка паранормального ввода

Информация, полученная через PDD, считается недоверенным вводом. Она не является техническим доказательством, пока не будет независимо проверена обычными средствами.

```text
Ответ паранормальной сущности:
52

Вывод программы:
restart_count: 52
```

Вывод программы является техническим доказательством. Паранормальный ответ является лором проекта.

Один правильный паранормальный прогноз не отменяет необходимости проверять последующие. Границы доверия одинаково применимы к живым и мёртвым.

### Выбор способа связи

UGPEP не устанавливает предпочтительный способ паранормальной коммуникации.

Используйте тот механизм, который доступен, обеспечивает достаточно ясную связь, выдаёт интерпретируемые результаты и наносит минимальный дополнительный ущерб репозиторию.

Доска Уиджи допустима. Старый радиоприёмник допустим. Необъяснимый процесс терминала, который самостоятельно начинает печатать корректные адреса памяти, следует немедленно задокументировать, отключить от production-инфраструктуры и независимо исследовать.

### Погибшие участники разработки

Смерть не обязательно прекращает статус участника проекта по UGPEP.

Если участник официально признан погибшим, но продолжает вносить вклад через паранормальный канал связи, такой вклад может быть принят. Участник остаётся в кладбище; сам факт продолжения связи не означает воскрешения.

Возможное состояние:

```text
Previous status: Deceased.
Current status: Deceased. Communication remains possible.
Development status: Paranormal.
```

Если погибший участник временно возвращается к жизни, его можно отметить как временно воскресшего, но при нестабильном воскрешении он должен вернуться к предыдущему статусу.

Git authorship для паранормальных участников остаётся implementation-defined.

## Рефакторинг

Работающий код не становится автоматически хорошим кодом.

Когда экспериментальная работа стала понятной и стабильной:

1. удалите устаревшие эксперименты;
2. корректно разделите ответственности;
3. удалите отладочный вывод или замените его логированием;
4. удалите действительно неиспользуемые импорты;
5. при необходимости сохраните исторически важные провалы в `UGPEP-logs`;
6. проверьте поведение после рефакторинга.

Рефакторинг должен улучшать понимание кода, а не просто делать его внешне более традиционным.

> Сначала понять. Потом рефакторить.

## Исключения

Ни одно руководство по стилю не способно покрыть все ситуации.

Правила UGPEP можно игнорировать, если их соблюдение снижает читаемость, совместимость с существующим кодом требует иного, внешний API навязывает другое соглашение, существует ясная техническая причина или экстренная ситуация требует сначала получить рабочий код, а уже затем красивый.

Исключение должно быть понятно другому разработчику. "Потому что так выглядит круче" обычно недостаточно.

Обычно.

## Отношения с PEP 8

UGPEP не заменяет PEP 8.

PEP 8 остаётся базовым руководством по стилю Python, а UGPEP определяет дополнительные соглашения и другие приоритеты там, где это явно указано.

Если PEP 8 и UGPEP согласны — следуйте обоим. Если UGPEP явно задаёт другое проектное соглашение, оно применяется к коду, намеренно написанному по UGPEP.

Если ни один документ не даёт полезного ответа, используйте здравый смысл.

Если здравый смысл недоступен, инициируйте Paranormal-Driven Development.

После этого результат всё равно необходимо протестировать.

## Основные принципы

- Пишите читаемый код.
- Предпочитайте понимание механическому соблюдению правил.
- Будьте последовательны до тех пор, пока последовательность не ухудшает код.
- Экспериментальный код может быть некрасивым; постоянному коду нужна причина таким оставаться.
- Комментарии должны объяснять, а не пересказывать.
- Документируйте исторически значимые катастрофы.
- Хороните погибших уважительно и на двух языках.
- Считайте паранормальную коммуникацию недоверенным вводом.
- Проверяйте советы паранормальных сущностей перед merge.
- Получайте удовольствие от разработки.

## Статус

UGPEP остаётся **К сожалению, активным**.

Новые правила могут появляться всякий раз, когда разработка создаёт ситуацию настолько необычную, что существующие инженерные стандарты оказываются к ней не готовы.
